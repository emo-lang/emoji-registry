# Emo Registry Design

Emo Registry is the package registry service for the Emo programming language — the
counterpart of rubygems.org for Ruby or npmjs.com for Node.js. This document is the
authoritative design for the package publishing and distribution mechanism, including
the wire protocol contract that the Emo compiler's HTTPS client will implement against.

The Emo compiler implementation lives in a sibling repository (`../emo`). The client-side
package mechanism (manifest, resolution, lockfile, caching) is already implemented there;
this service is the missing server side.

## 1. Constraints imposed by the language

| Emo characteristic | Consequence for the registry |
|---|---|
| `package.emo` manifest has a fixed schema of exactly 4 fields (`name`, `version`, `targets`, `deps`); old compilers reject unknown fields with E5100 | Metadata such as description, license, authors, README lives **only on the server**, returned via API — never written into the manifest |
| Versions are exact semver (`major.minor.patch`, digits only); no version ranges; MVS (Minimal Version Selection) resolution happens client-side | The server only needs to serve a version list and per-version dependency data; no server-side dependency solver |
| A package is a set of plain `.emo` source files and must contain `package.emo` | Publishing validation is simple: manifest must parse, `name`/`version` must match, sources only |
| Checksums feed `emo.lock` and the content-addressed client cache (`name-version-checksum` directories) | The server must reproduce the exact client digest algorithm to validate publishes and to make lockfiles verifiable |
| `targets` field (`native`, `wasm`, `typescript`, `beam`, `riscv64`) | Version records carry target metadata; indexes can be filtered by target |
| Scoped naming `owner/name`; top-level short names (`net`, `http`) reserved for the official stdlib | The ownership model is scope = account/organization; short names are gated by a server-side reserved list |
| Registry endpoint configured via the `EMO_REGISTRY` env var; private registries are a first-class scenario | The protocol must be simple enough to self-host, and even to serve as a static file tree |

### Checksum algorithm: SHA-256 from day one

The content digest is **SHA-256 over the sorted `(path, content)` pairs of all `.emo`
files**, concatenated as `path \0 content \0` (the same construction as the compiler's
`Registry.digest`, upgraded from MD5 to SHA-256 before any release ships). The same
algorithm covers both the content digest (what goes into `emo.lock`) and the archive
integrity hash. There is no algorithm prefix and no MD5 compatibility path — the
compiler-side change lands in the same window as this service.

## 2. Package format: the `.emoji` archive

The published artifact is a single gzip-compressed tar archive named:

```
<owner>--<name>--<version>.emoji
```

(Analogous to RubyGems' `<name>-<version>.gem`.) Contents:

```
foo--json_tools--1.2.0.emoji  (tar.gz)
├── package.emo          # manifest; the single source of truth for name/version/targets/deps
├── json_tools.emo       # sources
├── internal/...         # private subtrees preserved as-is
├── README.md            # optional, root only; rendered on the package page, never digested
└── EMO-METADATA.json    # server-generated: description/license/authors, per-file SHA-256 manifest
```

Invariants:

- The **content digest is computed over `.emo` files only**; `EMO-METADATA.json` and
  `README.md` are ignored by clients when unpacking so the digest of an unpacked
  archive always matches the lockfile checksum. (The compiler's `collect_files` only
  gathers `.emo` files, so shipping a README is safe for existing clients.)
- `package.emo` is written by the author and is authoritative; `EMO-METADATA.json` is
  generated by the server (the RubyGems `metadata.gz` analogue) and never feeds back
  into the manifest — old compilers are unaffected.

## 3. Ownership and naming

- A package name is `owner/name`. `owner` must be the publishing account or an
  organization the account belongs to.
- Top-level short names (no `/`) are reserved for the official stdlib (`net`, `http`,
  plus a reserved list for future stdlib names) and are rejected at registration time
  for ordinary accounts.
- Name validation: lowercase ASCII letters, digits, `_`, `-`; owner and name each
  1–64 chars.

## 4. Publishing (the `gem push` analogue)

```
emo publish
  → validate manifest locally, collect .emo files, compute SHA-256 digest, pack tar.gz
  → POST /api/v1/packages   (Authorization: Bearer <token>, body = .emoji archive)
```

Server-side validation pipeline (all must pass, otherwise 4xx with a stable error code):

1. Token valid with `push` scope.
2. Name is well-formed; owner matches the token's account/org; short names rejected
   unless reserved-list approved.
3. Version is valid exact semver and does not yet exist — **versions are immutable**;
   an existing version can never be overwritten, only yanked.
4. The archive unpacks cleanly; `package.emo` parses under the same restricted rules
   as the compiler (literal values only, no interpolation); manifest `name`/`version`
   match the publish.
5. Recomputed SHA-256 content digest matches the client-reported digest.
6. Archive stored (local `data/storage` or S3/R2 via the storage abstraction), DB
   rows written, indexes updated.

### Yank

`DELETE /api/v1/packages/:owner/:name/versions/:version` (or `emo publish --yank`).

Soft-delete semantics, deliberately more forgiving than RubyGems: a yanked version is
excluded from resolution indexes, but the archive stays downloadable so projects with
a pinned lockfile checksum do not break. Clients surface a warning when a lockfile
pins a yanked version.

### API tokens

Format `emo_<48 hex chars>`; only the SHA-256 hash is stored. Scopes: `push`, `yank`,
`read` (private packages, later phase). Created and revoked from the web UI; optional
per-package restriction and expiry.

## 5. Wire protocol

Base URL is whatever `EMO_REGISTRY` points to. Public read endpoints need no token.
Errors share one shape:

```json
{ "error": { "code": "version_exists", "message": "foo/json_tools 1.2.0 already published" } }
```

`code` is a stable machine-readable enum (`package_not_found`, `version_not_found`,
`version_exists`, `invalid_manifest`, `checksum_mismatch`, `unauthorized`, `forbidden`,
`name_reserved`); `message` is for humans only.

### Protocol A — bare-file compatibility layer

Mirrors the directory protocol the current compiler client already implements
(`Registry.versions` / `fetch` over a filesystem tree). Pointing
`EMO_REGISTRY=https://<host>` at this service works immediately:

```
GET /:owner/:name/versions                  → ["0.1.0", "0.2.0"]   (JSON array, yanked excluded)
GET /:owner/:name/:version/package.emo      → manifest source
GET /:owner/:name/:version/<path>.emo       → individual source file
```

Protocol A serves `.emo` sources only — it is the compiler's package channel, so
`README.md` and `EMO-METADATA.json` are deliberately not exposed here.

This layer is also trivially exportable as a static file tree for CDN hosting.

### Protocol B — JSON API (contract for the future HTTPS client)

The schemas below are **frozen**: the compiler's HTTPS client will hardcode against
them. Additive changes (new fields) are allowed; renaming or removing fields is a
protocol break.

#### B.1 Version list — the core MVS input

```
GET /api/v1/packages/:owner/:name/versions
```

```json
{
  "package": "foo/json_tools",
  "versions": [
    {
      "version": "1.2.0",
      "checksum": "9f2c...ab",
      "archive_sha256": "4d7e...01",
      "targets": ["native", "wasm"],
      "yanked": false,
      "published_at": "2026-09-30T12:00:00Z"
    }
  ]
}
```

- `checksum` — SHA-256 content digest over sorted `path\0content\0` of `.emo` files;
  exactly what the client writes into `emo.lock`.
- `archive_sha256` — hash of the `.emoji` file itself; download integrity only.
- `targets` — full list; filtering by build target is the client's job.
- `yanked` — yanked versions **appear in the list with the flag set** rather than
  vanishing, so a lockfile-pinned yanked version yields a clear warning instead of a
  confusing `version_not_found`. Resolution skips them.
- Array ordered by ascending semver.

#### B.2 Batch dependency query — speeds up MVS

```
GET /api/v1/dependencies?packages=foo/json_tools,baz/qux
```

```json
{
  "foo/json_tools": [
    { "version": "1.2.0", "deps": { "net": "0.1.0" }, "yanked": false }
  ],
  "baz/qux": []
}
```

- `deps` is verbatim the manifest's `deps {}` block (exact versions) — the client never
  parses manifest source during resolution.
- Unknown packages are simply absent from the response; clients treat that as
  `package_not_found`.
- Yanked versions are listed (clients skip them during resolution).

#### B.3 Archive download

```
GET /downloads/:owner--:name--:version.emoji
```

- 200: tar.gz body with `Digest: sha-256=<base64>` (RFC 9530) and `ETag` headers.
- Yanked versions remain downloadable; response carries `X-Emo-Yanked: true` so the
  client can warn.
- 404 uses the shared error shape.

#### B.4 Package metadata (web UI, `emo search`, `emo info` — not used at build time)

```
GET /api/v1/packages/:owner/:name
```

```json
{
  "name": "foo/json_tools",
  "description": "JSON utilities for Emo",
  "license": "MIT",
  "homepage": "https://example.com",
  "repository": "https://github.com/foo/json_tools",
  "downloads": 12345,
  "downloads_last_30d": 987,
  "owners": ["foo"],
  "latest_version": "1.2.0",
  "created_at": "...", "updated_at": "..."
}
```

Additive-only evolution.

#### B.5 Publish / yank

```
POST   /api/v1/packages
Authorization: Bearer <token>
Content-Type: application/octet-stream
Body: <raw .emoji archive bytes>
```

- Name and version are parsed from the archive's `package.emo` — **never** taken from
  URL or form parameters; one source of truth, no URL-vs-manifest mismatch.
- 201 returns the version object from B.1. 409 `version_exists` if already published;
  422 `invalid_manifest` with details.

```
DELETE /api/v1/packages/:owner/:name/versions/:version
Authorization: Bearer <token>
```

- Yank. 200 returns the version object with `yanked: true`; re-yanking is idempotent
  (200, not an error).

#### Metadata maintenance

Description, license, homepage, repository are not part of the archive and not part of
the publish request. They are maintained after publishing via the web UI or:

```
PATCH /api/v1/packages/:owner/:name   (Authorization: Bearer <token>)
```

This keeps the manifest's 4-field purity and keeps `emo publish` trivial.

## 6. Server data model

- `users` (username, email, password_digest)
- `organizations` (name, display_name, user_id) + `memberships` (organization_id,
  user_id, role) — usernames and organization names share one namespace: both act as
  package scopes, so registration rejects collisions across the two tables. Any
  member (owner or member role) may publish, yank and edit metadata under the
  organization's scope; only owners manage members.
- `api_tokens` (user_id, name, token_hash, scopes, expires_at, last_used_at)
- `packages` (owner_scope, name, description, license, homepage, repository, user_id,
  downloads)
- `versions` (package_id, version, checksum, archive_sha256, targets, deps, size,
  yanked_at, user_id, storage_key)
- `reserved_names` (name, reason) — the short-name reserved list, seeded at boot from
  the hardcoded stdlib list and extended by operators
- `downloads` (version_id, date, count) — per-version per-day aggregate, written
  synchronously on every download (the unique (version_id, date) index keeps rows
  canonical; a lost read-modify-write race at worst undercounts)

## 7. Security and governance

- Immutable versions + yank-does-not-delete → auditable supply chain.
- Reserved short-name list enforced at registration.
- Upload size limit (10 MB is generous for source-only packages); `.emo`-only file
  whitelist inside archives.
- Rate limiting: per-token-user on publish (30/hour), per-IP on signup/login
  (10/minute) and search (60/minute). In-process fixed windows; a Redis-backed
  limiter is a phase 3 concern.
- Only token hashes stored; passwords bcrypt.

## 8. Phased roadmap

1. **Phase 1 (working loop)**: accounts + tokens, publish/yank, both Protocol A and B,
   version lists, archive download, package detail web pages. The stock compiler can
   pull packages via Protocol A with `EMO_REGISTRY` pointed here.
2. **Phase 2**: batch dependencies API hardening.
3. **Phase 3**: static export to CDN, private packages with `read`-scoped tokens,
   Redis-backed download aggregation and rate limiting,
   `emo publish` / `emo search` CLI merged into the compiler repo.
