# Emo Registry Design

Emo Registry is the package registry service for the Emo programming language — the
counterpart of rubygems.org for Ruby or npmjs.com for Node.js. This document is the
authoritative design for the package publishing and distribution mechanism, including
the wire protocol contract that the Emo compiler's HTTPS client will implement against.

The Emo compiler implementation lives in a sibling repository (`../emo`). The client-side
package mechanism (manifest, resolution, lockfile, caching) is already implemented there;
this service is the missing server side.

## 1. Constraints imposed by the language

| Emo characteristic | Consequence for the registry |
|---|---|
| `package.emo` manifest has a fixed schema (`name`, `version`, `targets`, the optional `link` and `registry`, and `deps`); old compilers reject unknown fields with E5100 | Metadata such as description, license, authors, README lives **only on the server**, returned via API — never written into the manifest |
| Versions are exact semver (`major.minor.patch`, digits only); no version ranges; MVS (Minimal Version Selection) resolution happens client-side | The server only needs to serve a version list and per-version dependency data; no server-side dependency solver |
| A package is a set of plain `.emo` source files — plus the `.c`/`.h` native sources a c-target binding carries (T38.2) — and must contain `package.emo` | Publishing validation is simple: manifest must parse, `name`/`version` must match, sources only |
| Checksums feed `package.lock` and the content-addressed client cache (`name-version-checksum` directories) | The server must reproduce the exact client digest algorithm to validate publishes and to make lockfiles verifiable |
| `targets` field (`ocaml`, `c`, `wasm`, `typescript`, `beam`, `riscv64`) | Version records carry target metadata; indexes can be filtered by target |
| Scoped naming `owner/name`; top-level short names (`net`, `http`) reserved for the official stdlib | The ownership model is scope = account/organization; short names are gated by a server-side reserved list |
| Registry endpoint configured via the `EMO_REGISTRY` env var; private registries are a first-class scenario | The protocol must be simple enough to self-host, and even to serve as a static file tree |

### Checksum algorithm: SHA-256 from day one

The content digest is **SHA-256 over the sorted `(path, content)` pairs of all package
sources — every `.emo` file plus any `.c`/`.h` native sources**, concatenated as
`path \0 content \0` (the same construction as the compiler's `Registry.digest`, upgraded
from MD5 to SHA-256 before any release ships). The same algorithm covers both the content
digest (what goes into `package.lock`) and the archive integrity hash. There is no
algorithm prefix and no MD5 compatibility path — the compiler-side change lands in the
same window as this service.

## 2. Package format: the `.emoji` archive

The published artifact is a single gzip-compressed tar archive named:

```
<owner>-<name>-<version>.emoji
```

The single-dash joins are unambiguous because the name rule keeps every
part free of dashes (below), and a version is strict
major.minor.patch — so the file name is always exactly three
dash-separated segments. (Analogous to RubyGems' `<name>-<version>.gem`.)
Contents:

```
foo-json_tools-1.2.0.emoji  (tar.gz)
├── package.emo          # manifest; the single source of truth for name/version/targets/deps
├── json_tools.emo       # sources
├── internal/...         # private subtrees preserved as-is
├── shim.c / shim.h      # optional native sources a c-target binding compiles and links
├── README.md            # optional, root only; rendered on the package page, never digested
└── EMO-METADATA.json    # server-generated: description/license/authors, per-file SHA-256 manifest
```

Invariants:

- The **content digest is computed over the package's sources — `.emo` plus `.c`/`.h`**;
  `EMO-METADATA.json` and `README.md` are ignored by clients when unpacking so the digest
  of an unpacked archive always matches the lockfile checksum. (The compiler's
  `collect_files` gathers exactly `.emo`/`.c`/`.h`, so shipping a README is safe for
  existing clients.)
- `package.emo` is written by the author and is authoritative; `EMO-METADATA.json` is
  generated by the server (the RubyGems `metadata.gz` analogue) and never feeds back
  into the manifest — old compilers are unaffected.

## 3. Ownership and naming

- A package name is `owner/name`. `owner` must be the publishing account or an
  organization the account belongs to.
- Top-level short names (no `/`) are reserved for the official stdlib (`net`, `http`,
  plus a reserved list for future stdlib names) and are rejected at registration time
  for ordinary accounts.
- Name validation: a lowercase identifier — a letter first, then letters, digits, or `_`;
  no `-`. Owner and name are each 1–64 chars. The short name is what `require` binds in
  code, so the rule is the identifier alphabet itself; dash-free parts keep the download
  file name's single-dash joins unambiguous, and identifiers always render as code
  (monospace, never underlined), so a `_` never hides. The same rule governs account
  usernames and organization names, since they become the owner part of published names.

## 4. Publishing (the `gem push` analogue)

```
emo publish
  → validate manifest locally, collect the .emo/.c/.h sources, compute SHA-256 digest, pack tar.gz
  → POST /api/v1/packages   (Authorization: Bearer <token>, body = .emoji archive)
```

Server-side validation pipeline (all must pass, otherwise 4xx with a stable error code):

1. Token valid with `push` scope.
2. Name is well-formed; owner matches the token's account/org; short names rejected
   unless reserved-list approved.
3. Version is valid exact semver and does not yet exist — **versions are immutable**;
   an existing version can never be overwritten, only yanked.
4. The archive unpacks cleanly; `package.emo` parses under the same restricted rules
   as the compiler (literal values only, no interpolation); manifest `name`/`version`
   match the publish.
5. Recomputed SHA-256 content digest matches the client-reported digest.
6. Archive stored (local `data/storage` or S3/R2 via the storage abstraction), DB
   rows written, indexes updated.

### Yank

`DELETE /api/v1/packages/:owner/:name/versions/:version` (or `emo publish --yank`).

Soft-delete semantics, deliberately more forgiving than RubyGems: a yanked version is
excluded from resolution indexes, but the archive stays downloadable so projects with
a pinned lockfile checksum do not break. Clients surface a warning when a lockfile
pins a yanked version.

### API tokens

Format `emo_<48 hex chars>`; only the SHA-256 hash is stored. Scopes: `push`, `yank`,
`read` (private packages). Created and revoked from the web UI, or minted by
`emo emoji login` (push/yank/read, optional `--expires-in-days`, the expiry recorded
alongside the token locally); optional per-package restriction and expiry. A token
past its expiry is refused with the dedicated `token_expired` code, so clients can
prompt for a fresh login.

## 5. Wire protocol

Base URL is whatever `EMO_REGISTRY` points to. Public read endpoints need no token.
Errors share one shape:

```json
{ "error": { "code": "version_exists", "message": "foo/json_tools 1.2.0 already published" } }
```

`code` is a stable machine-readable enum (`package_not_found`, `version_not_found`,
`version_exists`, `invalid_manifest`, `checksum_mismatch`, `unauthorized`,
`token_expired`, `forbidden`, `name_reserved`, `owner_locked`); `message` is for
humans only.

### Private packages

A package's `visibility` is `public` (default) or `private`, switchable by the owning
scope via `PATCH /api/v1/packages/:owner/:name` or the package page. Every read surface
— Protocol A, the version list, dependency queries, package metadata, archive downloads
— requires authorization for private packages:

- The package's owner account, any member of the owning organization, and API tokens
  with the `read` scope belonging to those users may read. A `read` token reads every
  private package its user may read; there is no per-package restriction.
- Unauthorized requests get **exactly** the 404 `package_not_found` an unknown package
  gets — never 401/403 — so private names cannot be probed. `dependencies` omits
  unreadable packages, same as unknown ones.
- Clients authenticate with `Authorization: Bearer <token>`; the Emo toolchain reads
  the token from the `EMO_TOKEN` environment variable (new convention, additive only).

### Locked accounts and organizations

An admin can lock a user account or an organization (at `/admin/accounts`). A locked
scope's packages stay listed everywhere — search, profiles, org pages, the package
page and B.4 metadata keep working — but their content is frozen:

- The version list (B.1), dependency queries (B.2), archive downloads (B.3) and
  Protocol A answer `403 owner_locked` (message `该账号(组织）已被锁定`) for every
  package under the scope, so `emo deps resolve` stops with that error instead of
  quietly resolving nothing.
- Publishing, yanking and metadata edits under the scope are refused the same way.
- The admin account list, the profile and the org page show the 已锁定 status;
  unlocking takes effect immediately and restores everything.

### Protocol A — bare-file compatibility layer

Mirrors the directory protocol the current compiler client already implements
(`Registry.versions` / `fetch` over a filesystem tree). Pointing
`EMO_REGISTRY=https://<host>` at this service works immediately:

```
GET /:owner/:name/versions                  → ["0.1.0", "0.2.0"]   (JSON array, yanked excluded)
GET /:owner/:name/:version/package.emo      → manifest source
GET /:owner/:name/:version/<path>           → individual source file (.emo, .c, .h)
```

Protocol A serves package sources (`.emo` plus `.c`/`.h`) only — it is the compiler's
package channel, so `README.md` and `EMO-METADATA.json` are deliberately not exposed here.

This layer is also trivially exportable as a static file tree for CDN hosting:
`registry:export <dir>` (default `./dist-registry`) renders every public package as

```
<dir>/<owner>/<name>/versions                     # byte-identical to the protocol A response
<dir>/<owner>/<name>/<version>/<path>             # sources (.emo/.c/.h), yanked versions excluded
<dir>/downloads/<owner>-<name>-<version>.emoji    # archives, yanked included
<dir>/index.html                                  # human index, not part of the protocol
```

Private packages are skipped (the count is logged). The export overwrites files in
place and never deletes; clear the target directory first for an exact mirror.

### Protocol B — JSON API (contract for the future HTTPS client)

The schemas below are **frozen**: the compiler's HTTPS client will hardcode against
them. Additive changes (new fields) are allowed; renaming or removing fields is a
protocol break.

#### B.1 Version list — the core MVS input

```
GET /api/v1/packages/:owner/:name/versions
```

```json
{
  "package": "foo/json_tools",
  "versions": [
    {
      "version": "1.2.0",
      "checksum": "9f2c...ab",
      "archive_sha256": "4d7e...01",
      "targets": ["ocaml", "wasm"],
      "yanked": false,
      "published_at": "2026-09-30T12:00:00Z"
    }
  ]
}
```

- `checksum` — SHA-256 content digest over sorted `path\0content\0` of the package
  sources (`.emo` plus `.c`/`.h`); exactly what the client writes into `package.lock`.
- `archive_sha256` — hash of the `.emoji` file itself; download integrity only.
- `targets` — full list; filtering by build target is the client's job.
- `yanked` — yanked versions **appear in the list with the flag set** rather than
  vanishing, so a lockfile-pinned yanked version yields a clear warning instead of a
  confusing `version_not_found`. Resolution skips them.
- Array ordered by ascending semver.

#### B.2 Batch dependency query — speeds up MVS

```
GET /api/v1/dependencies?packages=foo/json_tools,baz/qux
```

```json
{
  "foo/json_tools": [
    { "version": "1.2.0", "deps": { "net": "0.1.0" }, "yanked": false }
  ],
  "baz/qux": []
}
```

- `deps` is verbatim the manifest's `deps {}` block (exact versions) — the client never
  parses manifest source during resolution.
- Unknown packages are simply absent from the response; clients treat that as
  `package_not_found`.
- Yanked versions are listed (clients skip them during resolution).

#### B.3 Archive download

```
GET /downloads/:owner-:name-:version.emoji
```

- 200: tar.gz body with `Digest: sha-256=<base64>` (RFC 9530) and `ETag` headers.
- Yanked versions remain downloadable; response carries `X-Emo-Yanked: true` so the
  client can warn.
- 404 uses the shared error shape.

#### B.4 Package metadata (web UI, `emo search`, `emo info` — not used at build time)

```
GET /api/v1/packages/:owner/:name
```

```json
{
  "name": "foo/json_tools",
  "description": "JSON utilities for Emo",
  "license": "MIT",
  "homepage": "https://example.com",
  "repository": "https://github.com/foo/json_tools",
  "downloads": 12345,
  "downloads_last_30d": 987,
  "owners": ["foo"],
  "latest_version": "1.2.0",
  "created_at": "...", "updated_at": "..."
}
```

Additive-only evolution.

#### B.5 Publish / yank

```
POST   /api/v1/packages
Authorization: Bearer <token>
Content-Type: application/octet-stream
Body: <raw .emoji archive bytes>
```

- Name and version are parsed from the archive's `package.emo` — **never** taken from
  URL or form parameters; one source of truth, no URL-vs-manifest mismatch.
- 201 returns the version object from B.1. 409 `version_exists` if already published;
  422 `invalid_manifest` with details.

```
DELETE /api/v1/packages/:owner/:name/versions/:version
Authorization: Bearer <token>
```

- Yank. 200 returns the version object with `yanked: true`; re-yanking is idempotent
  (200, not an error).

#### Metadata maintenance

Description, license, homepage, repository are not part of the archive and not part of
the publish request. They are maintained after publishing via the web UI or:

```
PATCH /api/v1/packages/:owner/:name   (Authorization: Bearer <token>)
```

This keeps the manifest's fixed-schema purity and keeps `emo publish` trivial.

## 6. Server data model

- `users` (username, email, password_digest, locked, totp_secret, totp_enabled)
  — `totp_secret` is the Base32 shared secret, empty until enrollment;
  `totp_enabled` flips only after the first code is verified
- `sessions` (user_id, token, expires_at, totp_pending) — `totp_pending` marks a
  signup/login session that has passed the password check but not yet the 2FA
  step (15-minute TTL); such a session cannot read any page or `/api/v1` route
  outside the enrollment/challenge flow
- `totp_recovery_codes` (user_id, code_hash, used_at) — ten SHA-256 hashes per
  enrollment, single use; regenerating replaces the whole set
- `organizations` (name, display_name, user_id, locked) + `memberships` (organization_id,
  user_id, role) — usernames and organization names share one namespace: both act as
  package scopes, so registration rejects collisions across the two tables. Any
  member (owner or member role) may publish, yank and edit metadata under the
  organization's scope; only owners manage members.
- `api_tokens` (user_id, name, token_hash, scopes, expires_at, last_used_at)
- `packages` (owner_scope, name, description, license, homepage, repository, user_id,
  downloads)
- `versions` (package_id, version, checksum, archive_sha256, targets, deps, size,
  yanked_at, user_id, storage_key)
- `reserved_names` (name, reason) — the short-name reserved list, seeded at boot from
  the hardcoded stdlib list and extended by operators; an entry is a plain name
  (exact match) or a case-insensitive regular expression (e.g. `^emo`)
- `downloads` (version_id, date, count) — per-version per-day aggregate. With
  `REDIS` configured, downloads are counted with INCR and flushed into this table
  by a background flusher every minute; without Redis the write is synchronous.

## 7. Security and governance

- Immutable versions + yank-does-not-delete → auditable supply chain.
- Reserved short-name list enforced at registration; the DB-managed list is edited
  by admins at `/admin/reserved` (the built-in stdlib list is compiled in and
  read-only).
- Admin console at `/admin` (all packages listed newest first, private included;
  non-admins get 404). An admin is either a site account promoted with
  `admin:grant <username>`, or the `ADMIN_USERNAME`/`ADMIN_PASSWORD` credentials
  signed in at `/admin/login` — the issued cookie is HMAC-signed with a key
  derived from those credentials, so rotating either invalidates every session.
- Force delete (purge): typing "I want to purge this package <owner>/<name>"
  (exact match, re-verified server-side) removes the package's download
  aggregates, versions, the package row and every stored object — file names
  are enumerated from the canonical archive itself, since the storage layer
  has no listing. There is no undo; this is the only path that deletes
  published content (yank keeps archives downloadable).
- Account lock: admins freeze an account or organization from `/admin/accounts`.
  Its packages stay listed, but every resolution read, download and write under
  the scope answers `403 owner_locked` until it is unlocked.
- Upload size limit (10 MB is generous for source-only packages); only `.emo`/`.c`/`.h`
  sources (plus a root README.md) are whitelisted inside archives.
- Rate limiting: per-token-user on publish (30/hour), per-IP on signup/login
  (10/minute) and search (60/minute). Counters live in Redis when `REDIS` is
  configured, otherwise in-process fixed windows.
- Only token hashes stored; passwords bcrypt.
- Mandatory TOTP two-factor authentication (RFC 6238, SHA-1, 30 s step, 6
  digits, ±1 step for clock skew). Signup and the first page load after every
  login land on enrollment/challenge; the rest of the site and `/api/v1` stay
  closed to the pending session. Successful verification rotates the session
  token and extends it to the normal TTL, so a pre-2FA cookie cannot be
  replayed. Ten one-time recovery codes per enrollment are stored hashed and
  consumed atomically; disabling 2FA is not offered, only an admin reset.
- Once an account has enrolled, HTTP Basic Auth (email + password) is rejected
  with `401 totp_required`; callers mint API tokens from the web session and
  then use Bearer tokens. `POST /api/v1/login` requires a `code` for enrolled
  accounts and refuses with `403 totp_setup_required` before enrollment.
- Admins can reset a user's 2FA from `/admin/accounts`
  (`POST /admin/accounts/users/:id/reset-2fa`), which clears the secret and
  recovery codes and drops all of that user's sessions.

## 8. Phased roadmap

1. **Phase 1 (working loop)**: accounts + tokens, publish/yank, both Protocol A and B,
   version lists, archive download, package detail web pages. The stock compiler can
   pull packages via Protocol A with `EMO_REGISTRY` pointed here.
2. **Phase 2**: batch dependencies API hardening.
3. **Phase 3**: `emo publish` / `emo search` CLI merged into the compiler repo.
